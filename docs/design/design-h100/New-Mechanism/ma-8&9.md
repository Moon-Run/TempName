# MA8＋MA9：在 F4-cache 上叠加精确零梯度统计融合

**2026-10-27，组合实验已实现，尚未运行组合八卡性能测试。** 本轮只比较 **F4-cache** 和 **F4-cache-zcount**：两组都使用 MA8-v2 的前向激活保留，组合组再启用已验证的 MA9 优化器零梯度统计融合。要回答的是“MA9 加到 F4-cache 后是否还有完整训练增量”。

在 H100 容器的 `TempName` 仓库根目录执行：

```bash
bash tools/h100/phase6/run_ma89.sh --execute
```

## 1. 两组定义与已有证据

| 实验组 | 模型前后向 | optimizer 零梯度统计 |
| --- | --- | --- |
| **F4-cache，对照** | 原 MA8-v2：QKV／FC1 前向保留独立完整输入，反向复用 | 原逐参数 `count_nonzero`、减法和按序累加 |
| **F4-cache-zcount，组合** | 与对照相同的原 MA8-v2 | 原 MA9：两个 CUDA kernel 完成精确多张量统计 |

**没有原始 F4 第三组。** 两组的选择性量化、arrival order、双工作区、row projection GEMM／发布屏障／decoder＋bias/residual、LayerNorm，以及梯度范数、裁剪、Adam 和清梯度均沿用原路径。共同的缓存实现继续使用没有新增逐调用包装的 MA8-v2；不重新加入 v1 的列模块计数、输入／指针检查或 column `record_function`。

已有单机制结果仅说明组合值得测试：

| 已完成实验 | 同期对照→候选均值 ms/step | 配对收益 %［95% CI］ |
| --- | --- | --- |
| [MA8-v2](ma-8.md#10-ma8-v2-八卡结果与离线复核2026-10-27)，F4→F4-cache | 502.381→474.004 | +5.648 [ +5.252, +6.035 ] |
| [MA9](ma-9.md#9-ma9-首轮八卡实测与离线复核2026-10-27)，F4→F4-zcount | 503.310→489.878 | +2.669 [ +2.306, +3.062 ] |

两项都只有一次独立 trial，来自不同批次。**不能相加两个百分比，也不能从 474.004 ms 中直接减去 MA9 的历史 13.431 ms，作为组合结果。** 本轮收益的分母必须是本批同期 F4-cache。

## 2. 为什么可以叠加，以及哪里可能不叠加

MA8 与 MA9 改动两个不同的阶段：

```text
两组共同：
    前向 QKV／FC1 AllGather → 原 GEMM，并保存完整输入
    反向复用完整输入 → 原 dgrad／ReduceScatter／wgrad
    四个 microbatch 的梯度累积完成
    原梯度范数与裁剪

F4-cache：
    原逐参数零统计 → 原标量 AllReduce／item → 原 Adam → 原清梯度

F4-cache-zcount：
    MA9 两个零统计 kernel → 原标量 AllReduce／item → 原 Adam → 原清梯度
```

MA8 删除的是每 rank 每 step 256 次重复反向输入 AllGather。MA9 读取已经准备好的原 FP32 梯度，把零统计计算 kernel 从 rank0 的 1945 次、其他 rank 的 970 次收敛为两次。统计不写梯度；MA8 也不改变该统计的参数选择、dtype 或求值规则，因而两项机制具备组合的数值基础。

但执行时间不必简单相加。MA8 会改变 rank 到达 optimizer 的时刻、缓存状态和分配器行为，可能改变 MA9 可节省的提交与同步等待。组合还必须保持 MA9 缓存的梯度地址稳定；原实现逐次检查地址、顺序与 stream，发生漂移即失败。完整 smoke 和正式配对测试负责验证这些条件，不用单机制成功替代组合验证。

两组都承担 MA8 约 1 GiB／rank 的逻辑激活保留成本，因此它不是本轮候选相对对照新增的成本。MA9 的描述表和分块计数 workspace 沿用原实现；完整报告仍测量双方 allocated／reserved 峰值，不预先承诺峰值可相加或一定下降。

## 3. 实现与对照身份

本轮没有重写两项算法：

- 两组都直接调用原 [ma8_adapter.py](../../../../tools/h100/phase6/ma8_adapter.py) 的 `install_activation_cache(raw, 'F4-cache')`，只在初始化执行一次。两组实际使用同一个 `_MA8CachedRawLinear`、同一源码指纹和同样的 64 个列模块。
- 仅组合组在初始化时调用原 [ma9_adapter.py](../../../../tools/h100/phase6/ma9_adapter.py) 的 `install_zero_count`。F4-cache 对照不安装 MA9，不为对照添加统计 tracker 或包装。
- [ma89_sources.py](../../../../tools/h100/phase6/ma89_sources.py) 直接复用原 MA9 native 变换与 [ma9_zero_count.cuh](../../../../tools/h100/phase6/ma9_zero_count.cuh)。对照 native 文件仍为注册 F4 的原字节；候选仅增加原 MA9 header、runtime include 和三个明确接口导出。原投影源码不变。
- 保留 MA9 的动态导出检查：构建完成、复用和在线 worker 启动前通过 `nm -D --defined-only` 验证候选三个 `ma9_zero_count_*` 接口存在，对照不暴露这些接口，避免重复此前“对象编译成功但动态符号不可见”的失败。
- [ma89_fullstep.py](../../../../tools/h100/phase6/ma89_fullstep.py) 固定原 row adapter／TACO 字节与原八个训练函数、计时循环的 AST。仅在循环外安装共同缓存及候选统计实现，冻结全部源码与 helper 供只读离线复算。

MA9 原有的每 optimizer step 描述表检查和状态记录保留在组合组，是本次复用的已验证实现的一部分；没有新增逐层诊断。其 `ma9.optimizer.zero_count` 标记只在独立 profile 中出现，正式计时不会启用该标记。MA8 两组均不增加 column 标记或外层 autograd Function。

### 精确性要求

组合仍保持原 shared／TP duplicate／缺失梯度过滤及参数顺序。`+0/-0` 计零，NaN、Inf、非零 subnormal 不计零；先得到每参数 int64 计数，再按原顺序逐项转 FP32、逐项舍入累加。不能改为先把所有整数相加再转 FP32。原单标量 TP8 SUM AllReduce 和 `.item()` 保留在 Adam 之前。

## 4. 组合测试协议

| 项目 | 设置 |
| --- | --- |
| 两组及主比较 | `F4-cache`、`F4-cache-zcount`；唯一主比较 `F4-cache-zcount/F4-cache` |
| 模型 | TP8、PP=CP=DP=1、32 层、hidden 4096、sequence 2048、global batch 4、四个 microbatch、BF16、零 dropout |
| 环境 | 原 CUDA 12.4 runtime／12.8 build、`CUDA_DEVICE_MAX_CONNECTIONS=1`、`NCCL_NVLS_ENABLE=0` |
| 正式窗口 | 10 步预热＋50 步完整 optimizer step，包含统计、更新和清梯度 |
| 配对 | 每 trial 八个平衡 AB／BA 块、16 窗口、800 个正式步骤；可选两 trial |
| 时间和统计 | 每窗取八 rank 最大墙钟／50；完整块配对对数比、10000 次 bootstrap 95% CI，保留全部窗口 |

启动顺序为：构建及导出验证 → 原 row 投影算子正确性／计时／profile → 组合完整模型 smoke → 两组完整训练计时 → 独立完整 step profile。

算子阶段仅检查两组原 row 投影保持一致，既不执行缓存前后向，也不执行 optimizer 零统计，不能拿它的耗时宣称组合增量。

### 正确性检查

1. 完整模型 smoke 两步预热、三步核对，逐 rank 比较全部 **389 个可训练参数张量**的梯度和更新指纹。正式窗口比较同块同 rank 的 loss、grad norm 与最终参数指纹。
2. 组合组沿用 MA9 的 smoke 核对：每次统计比较逐参数 native int64 零数，并额外执行原统计函数，要求分布式归约后的返回值完全一致。实际 CUDA 边界 self-test 覆盖空输入、signed zero、NaN／Inf／subnormal、chunk 尾部、超过 `2^24` 的顺序舍入和 scratch 重用。
3. 原统计参考计算只在 smoke 中执行；正式窗口不增加零统计返回值的逐步记录，不给 F4-cache 的 `step` 添加捕获包装。报告中的零统计等价来自上述精确 smoke 检查，不声称记录了正式零统计轨迹。
4. 拒绝候选回退、缺失模块、错误梯度布局、源文件漂移和未知 runtime；失败不放宽数值门槛。

### 两项机制必须同时出现在实际路径

[ma89_profile.py](../../../../tools/h100/phase6/ma89_profile.py) 组合原 MA8-v2 与 MA9 的检查器：

| 每 rank 每独立 profile step | F4-cache | F4-cache-zcount |
| --- | ---: | ---: |
| 原缓存 QKV／FC1 调用 | 256 | 256 |
| 目标反向输入 AllGather | 0 | 0 |
| 原前向输入 AllGather／dgrad ReduceScatter，各自 | 256 | 256 |
| 未修改的原 LM head | 4 | 4 |
| optimizer 原 `count_nonzero`，rank0／其他 | 389／194 | 0／0 |
| 零统计计算 kernel，rank0／其他 | 1945／970 | 2／2 |
| 原单标量 TP8 AllReduce／4-byte 统计读回，各自 | 1 | 1 |

原 row 前后向路径和 Adam 等待统计完成的依赖同时检查。把未缓存的原 F4、单独 MA9 或带 v1 column 包装的路径改名成组合组，均不能通过。新增 profile 组合检查只在独立 profile／离线分析中执行，不进入正式训练计时循环。

## 5. 怎样判断是否更快

**“确认更快”要求相对同期 F4-cache 的配对点估计与 95% CI 下界都大于 0，并通过数值和完整路径检查。** 对应 `increment_over_F4_cache_validated["F4-cache-zcount"]`。

同时保留 **相对 F4-cache 再减少 2%** 的增量目标，分别报告点估计达到 2% 与 CI 下界达到 2%；后者通过才置 `target_validated=true`。例如历史 474.004 ms 的 2% 约为 9.480 ms，仅用于预算量级，正式计算使用本次对照。若确认正增量但小于 2%，仍报告更快及实际幅度，不把它归为无收益。

最终验收以 `batch-state.json` 为准。计时完成只产生统计判断；完整 profile 成功复算后，才将正增量／2% 字段写入最终批次状态。profile 失败时不把中途正数发布为完整通过；负收益和区间跨零也保留结果，不自动换配置筛选更快窗口。每个请求的 trial 分别判定，单 trial 仍属于探索。

## 6. 启动与结果

入口为 [run_ma89.sh](../../../../tools/h100/phase6/run_ma89.sh)：

```bash
# 只预览两组计划，不创建批次、不查询 GPU
bash tools/h100/phase6/run_ma89.sh

# 后台完整执行一次两组对比
bash tools/h100/phase6/run_ma89.sh --execute

# 两个独立 trial
bash tools/h100/phase6/run_ma89.sh --trials 2 --execute

# 在当前终端前台执行
bash tools/h100/phase6/run_ma89.sh --foreground --execute
```

支持 `MA89_PYTHON=/path/to/python`、`--out` 和 `--ma89-build`。复用参数只接受该组合实验验证过的完整 build；历史 MA8／MA9 build 不能改名冒充。新批次默认位于 `logs/h100/phase6/ma89-v1-cache-zcount-…`，原实验代码、报告和日志不被覆盖。

主要查看：

- `batch-state.json`：阶段、最终路径验证和相对 F4-cache 的验收结果。
- `fullstep/preflight.json`：完整模型 smoke 数值门槛。
- `fullstep/report.json`、`report.md`：两组全部窗口、平均步时、配对收益／CI及显存峰值；`target_reference` 为 `F4-cache`。
- `fullstep/profile-summary.json`：两组缓存路径，以及原／融合零统计的真实 kernel 与同步证据。
- `fullstep/results/`：原始 rank 记录与 trace；冻结控制器支持只读离线重算。

## 7. 本地验证边界

**53 项本地测试通过，零跳过**：8 项构建、8 项冻结 worker、17 项完整训练控制器／冻结复算、8 项启动器、10 项组合 profile、2 项 BF16／FP32 组合数值测试。补齐构建依赖后还重新核对了最终 native 来源身份。记录见 [validation.json](../../../../outputs/h100/phase6/ma89-validation-20261027/validation.json)。

本轮复用两项已经单独上机验证的实现，并新增组合安装、两组身份、构建导出、数值与路径检查：

- 构建检查验证对照 native 字节与原 F4 一致，组合组仅加入原 MA9 helper／include／导出项；通过实际 CPU ELF 导出检查与重记哈希后仍拒绝非法改动的回归。这里的 CPU ELF 只用于验证导出与启动逻辑，不是 GPU 动态库。
- 冻结 worker 在导入 Torch 前验证来源与导出，两个组名均可到达 GPU 初始化边界；旧组名、遗漏缓存、错误统计路径和列包装会被拒绝。
- BF16／FP32 的组合 CPU 数值检查，每组执行三次更新、每次四个 microbatch。两组都运行原 MA8 缓存，原 `ChainedOptimizer.step/count_zeros` 与仅候选 MA9 安装共同执行；梯度、统计值及更新参数一致。统计值随输入改变，原稳定梯度地址复用时不会读到旧统计，描述表只初始化一次，统计不修改梯度。TP collective、native ABI 与参数更新回调为测试替身，不代表真实 NCCL／CUDA／Adam 验证。
- 组合 profile 检查同时要求两项机制；另用八份实际 MA8-v2 F4-cache trace 回放验证本次对照路径，每 rank 均为 256 次缓存列调用、零次目标反向 AllGather，并保留原 1945／970 次 optimizer 统计计算 kernel。
- 生成代码、冻结控制器独立导入、实际 shell 预览、两组配对、完整指纹、负结果保留及 profile 失败时不发布最终正验收均已检查。

验证记录保存在 [ma89-validation-20261027](../../../../outputs/h100/phase6/ma89-validation-20261027/)。**尚未运行组合八卡测试，没有组合步时或增量结果。** 是否比 F4-cache 更快，必须由本轮脚本的完整训练配对回答。
