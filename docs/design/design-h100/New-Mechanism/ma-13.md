## 1. 当前基线与新目标

[MA11](ma-11.md#8-ma11-v1-八卡实测有正增量但未达到2目标) 已将同期 MA89 的平均步时从 459.638 ms 降至 **450.6624015075795 ms**，完整块配对收益为 +1.952%［95% CI：+1.711%, +2.271%］。这个结果支持保留 MA11，但不能把 1.952% 舍入为已达到 2%。本次在 MA11 上继续测量独立增量。

| 组别 | 策略 ID | 实际执行 |
| --- | --- | --- |
| 对照 MA11 | `F4-cache-zcount-csoftmax` | 原 F4＋MA8-v2 缓存＋MA9 零统计＋原 MA11 前后向 |
| 候选 MA13 | `F4-cache-zcount-csoftmax-resident` | 完整 MA11，仅替换 softmax 前向 kernel |

历史量级的预算是：

```text
450.6624015075795 × 2% = 9.013248 ms / optimizer step
9.013248 ms ÷ (32层 × 4 microbatch) = 70.416 μs / attention forward
历史量级下的目标步时 ≈ 441.649153 ms
```

**实际判定只使用新批次同期 MA11 对照。** 441.649 ms 只是历史量级换算；不能把新候选与历史 450.662 ms 跨批次相减，也不能改用较慢的 MA89/F4 作为分母。

## 2. 从 MA11 实际路径找到仍然存在的工作

重新解析 MA11 批次 `ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643` 候选的八份 trace，逐次关联 autograd、CPU marker、CUDA launch 和 GPU kernel。每 rank 每 optimizer step 均为 128 次前向与 128 次反向。

| 原 MA11 路径 | 每次 launch | 每 rank 每步工作量的八 rank 中位数 |
| --- | --- | ---: |
| softmax forward | 8192 blocks × 1024 threads | 14.381526 ms |
| softmax backward | 8192 blocks × 128 threads | 5.186632 ms |
| forward CPU autograd 区间 | 128 次 | 16.338877 ms |
| forward 内部 CPU marker 区间 | 128 次 | 12.109727 ms |
| forward CUDA launch CPU 区间 | 128 次 | 1.215869 ms |

三种 CPU 区间互相嵌套，不能相加；CPU 和 GPU 也有重叠。**表中是有 profiler 时的工作量或区间，不是无 profiler 的关键路径净耗时。** 原始 trace 哈希、逐 rank 数据及复算程序见 [baseline-analysis.json](../../../../outputs/h100/phase6/ma13-validation-20261027/baseline-analysis.json) 和 [baseline-analysis.py](../../../../outputs/h100/phase6/ma13-validation-20261027/baseline-analysis.py)。

原 [ma11_softmax.cuh](../../../../tools/h100/phase6/ma11_softmax.cuh) 暴露了两个可删除的执行对象：

1. **空 warp。** 每行 2048 个 BF16 元素，每线程读 8 个，所以只有线程 0–255、即前 8 个 warp 持有数据。为了照搬 ATen 数值树，MA11 仍启动 1024 个线程；余下 24 个 warp 仅对 `-FLT_MAX` 或 `+0` 做归约，却占据线程资源并参加 CTA 同步。
2. **重复的指数和共享缓存。** 分母阶段计算一遍 `exp(score−max)`，输出阶段再计算一遍；中间把整行 BF16 分数放在 4096 B shared memory 中。对原实现重新编译并检查 PTX、SASS，确认前向展开后确有 **16 个指数核心**，编译器没有自动将两次求值合并。

指数次数是每个活跃线程展开后的静态指令数量，不能称为每个 kernel 总共只算 16 次。原来每个有效元素两次求值，候选为一次；两组仍读取全部元素和实际 bool mask，写出全部概率。

## 3. 新机制：逻辑归约树不变，压缩其物理执行

### 3.1. 将空 warp 的结果直接提供给第二级归约

MA13 的 256 个线程各自拥有与原线程 0–255 相同的 8 个元素，保持原局部 max 和八项 FP32 顺序求和。每个真实 warp 仍执行原 `16/8/4/2/1` shuffle 序列。

第二级仍使用完整的 32 个 lane：

```text
原 MA11：
  8 个数据 warp 的结果 + 24 个空 warp 算出的中性结果
  → 原 32-lane shuffle 树 → row max / denominator

MA13：
  8 个数据 warp 的同一结果 + 24 个直接给定的中性常量
  → 同一 32-lane shuffle 树 → row max / denominator
```

max 的空 warp 结果为 `-FLT_MAX`，sum 的空 warp 结果为正零。候选的首 warp 在 lane 8–31 中直接使用这些值。**没有把第二级改为八 lane 求和，也没有重新关联浮点加法。** 仍保留每个阶段的 CTA 同步和原第二级运算顺序；shared memory 只需存放八个真实 warp 的结果。

这使不携带数据的 768 个线程无需存在，同时保持原数值树。H100 每 SM 的上限为 64 个 warp、64K 个 32-bit 寄存器；按线程上限计算，原 1024-thread CTA 至多两行同时驻留，新 256-thread CTA 可以容纳更多行。实际并发还受编译资源与调度限制，不能将线程数缩减四倍解释为性能必然提高四倍。硬件上限见 [NVIDIA Hopper Tuning Guide §1.4.1.1](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html#occupancy)。

### 3.2. 指数跨越分母归约驻留

每个线程把掩码后的八个 BF16 分数留在寄存器中。得到 row max 后，对每项调用一次与 MA11 相同的 `__nv_expf`，保存为 FP32 `exponent[8]`：

```text
读取 scores 和实际 mask → 原 max 树
→ 每元素一次精确指数求值，保存 FP32 exponent[8]
→ 原八项顺序加法及原 sum 树
→ 复用 exponent[i] / denominator → BF16 probability
```

寄存器值跨越归约存活，省去第二轮指数求值，也不再需要 BF16 shared score cache。仍用 `__fdiv_rn`，不改为近似倒数；不把指数先舍入成 BF16；不利用三角掩码跳过元素。归约依据继续是冻结的 [PyTorch v2.6.0 SoftMax.cu](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/native/cuda/SoftMax.cu) 与 [block_reduce.cuh](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/native/cuda/block_reduce.cuh)，随源保留原许可证。

### 3.3. 完整训练中的替换边界

```text
原 QK baddbmm
→ MA13 前向：虚拟空 warp＋指数驻留
→ 原 PV bmm

原 PV backward
→ 原 MA11 softmax backward（相同 CUDA 函数）
→ 原 QK backward
```

每步仍为 128 个 softmax 前向和 128 个反向 kernel，调用次数、概率矩阵尺寸和 autograd 保存对象均不变。收益假设来自每个前向内部真实执行工作与无效线程占用的下降。没有新增 stream、collective、训练期 buffer、梯度 hook 或 Python 队列。

实现为 [ma13_softmax.cuh](../../../../tools/h100/phase6/ma13_softmax.cuh) 和 [ma13_adapter.py](../../../../tools/h100/phase6/ma13_adapter.py)。候选继承原 MA11 的张量检查、分配、当前 stream 提交和 backward；模块安装仅初始化一次，正式计时不增加包装层或逐次 oracle。对照直接安装原 `ma11_adapter.install_softmax`。

## 4. 与此前失败方向的区别

| 既往方向 | 已有结果 | MA13 的变化位置 |

这里的“新”指现有仓库实验序列中未尝试的机制，不声称学术首创。它也不是再打开现成 fused-softmax 开关、FlashAttention 或更换近似指数算法。

## 5. 正确性门槛和失败条件

- 固定原 TP8、32 层、hidden4096、sequence2048、BF16、零 attention dropout、无 recompute／CUDA Graph 配置；每次输入为 `[1,4,2048,2048]`，实际 bool mask 为 `[1,1,2048,2048]`。不支持的配置直接拒绝。
- 保留原 QK 缩放，mask sentinel 仍为 `BF16(-10000)`，实际值 −9984，不能改成负无穷。保留局部 `fmaxf` 与跨线程 `maximum` 的操作数顺序、FP32 逐项舍入、精确除法及最终 BF16 舍入。
- 候选放在单独 CUDA 编译单元，仅该文件恢复 `--ftz=false --prec-div=true --prec-sqrt=true`；原 MA11 的文件及原编译选项不改。两组共同具有 MA11 三个 ABI，候选额外具有 MA13 两个 ABI，构建、复用和 worker 均检查实际动态符号。
- 对照 smoke 保留原六类 GPU／ATen 前后向字节检查。候选扩展为十六类：全部与实际 MA11 前后向逐字节比较；原六类及七类新增有限输出情况也与 ATen 逐字节比较。另三类 Inf／NaN 情况用原 MA11 的位模式作 oracle，不额外要求旧 MA11 未承诺的 ATen NaN payload。包括全 mask、非三角 mask、有限 sentinel、ties、正负零、subnormal、极值等；不消耗训练 RNG。
- 两组完整模型 smoke 的每次前后向仍与原 ATen 做字节对照，并核对每 rank 全部 389 个参数的梯度／更新指纹。正式窗口继续核对 loss／grad norm 轨迹和最终参数指纹，不放宽门槛。所有自测与逐次数值审计均不进入正式计时。

理论上可消除的工作不等于必然收益。按历史前向 profile 的14.381526 ms量级，要独自承担9.013248 ms目标，需净减少约 **62.67%** 的该量级工作；这只是判断难度的预算，不能拿不同计时口径组成性能预测。即使整个前向快两倍，在这种粗略换算下也仅省约7.19 ms，未必足够2%。寄存器压力、原主机／通信重叠、局部提速后暴露出的其他瓶颈都可能使结果不足目标。

**可推翻本假设的结果：** GPU 字节检查失败则停止；新前向本身不快则机制未兑现；前向变快但整步 CI 跨零则没有验证关键路径收益；整步正增量但未到2%则如实记录，不转而扫描 decoder 配置或挑选最快窗口。

## 6. 启动、对比协议和产物

```bash
# 预览：不创建批次、不构建、不查询 GPU

  --ma13-build /absolute/path/to/verified-ma13-build --execute
```

启动器沿用 `run_ma8.sh` 的恢复环境：服务器默认 CUDA12.8 构建、CUDA12.4 运行及八张 H100；可通过 `MA13_PYTHON` 指定解释器，通过 `--build-cuda-home`／`--cuda-home` 指定工具链。MA11、MA89、MA12 build 均不能冒充 MA13 build 复用。

每个 trial 保留 **8 个 AB/BA 平衡块、16 个独立进程窗口、128 份正式 rank 记录、800 个正式 optimizer step**。每窗口 10 步预热＋50 步正式，用八 rank 最大窗口墙钟／50 计算完整 optimizer step，包含前后向、通信、统计、参数更新和清梯度。按完整配对块对数耗时比做 10,000 次 bootstrap，保留所有慢窗口和负结果。

执行顺序为：构建 → 原 row projection 数值／计时／profile 预检 → 完整模型 smoke → 配对完整训练计时 → 独立完整训练 profile。原 row projection 未改变，其阶段只核对共同路径，不拿它证明新 softmax 加速。

独立 [ma13_profile.py](../../../../tools/h100/phase6/ma13_profile.py) 必须同时确认：

1. 对照128次 `ma11_softmax_forward_kernel`（1024 threads），候选128次 `ma13_softmax_forward_kernel`（256 threads），两组各128次原 `ma11_softmax_backward_kernel`（128 threads）。每个 kernel 有唯一 marker／launch 归属，grid 均为8192，前后依赖与 compute stream 正确；拒绝回退或两组实现串用。
2. 原 QK／PV 及其反向 GEMM 完整，旧 ATen softmax、注意力 mask／view 重建没有恢复，LM-head 四次 CopySlices 保留。
3. 两组共同的 MA8 仍删除256次目标反向输入 AllGather，MA9 仍只有两个统计 kernel 并保留原标量 AllReduce，F4 row producer／barrier／decoder 和 row backward 不变。

| 判定 | 条件 |
| --- | --- |
| `increment_over_MA11_validated` | 每 trial 配对点估计 >0 且95% CI下界 >0，数值和最终路径通过 |
| `target_point_observed` | 每 trial 点估计 ≥2%；单独成立不代表稳定达标 |
| 最终 `target_validated` | 每 trial 点估计及95% CI下界均 ≥2%，且完整正确性与独立 profile 通过 |

产物位于打印的 `logs/h100/phase6/ma13-v1-resident-softmax-.../`：
